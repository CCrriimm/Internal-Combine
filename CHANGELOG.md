# Changelog

## Unreleased

- **The packet build was the biggest line in the tick, and it was re-reading every target every frame.** With the four sub-timers finally labelled in the order they are emitted (see below), a 22-target fight read: `rest=0.538` = `sync 0.002 + local 0.004 + ser 0.458 + wr 0.075`. `_serialize_frame_data` was pulling name, hero id, monster flag, hp, max hp, armor and max armor out of the engine for every target on every tick - eight reads each, forty thousand a second at 227 fps, for a health bar that cannot show more than 10 Hz.
  - Name, hero and monster flag are now cached per entity for 1 s (`STATIC_TTL`); hp/armor for 100 ms (`VITALS_TTL`). A second tick with the same targets now reads **nothing** from the engine, and the packet is byte-identical.
  - The 64 KB packet buffer is allocated once instead of per tick (it was zeroing 64 KB to use 8).
- **Team relations were decided twice per target per gather** - `game_logic.IsTeammate` and `CanDamage`, `team=0.164` averaged over every tick, ~0.6 ms per gather at 22 targets. Cached per entity keyed on the local team it was decided against, 1 s TTL, dropped with the space.
- **`[sys:tick]`'s four new fields were labelled in the wrong order.** The values were emitted right after `rest` but the labels sat after `collect`, so `bone=` was really sync, `team=` was really serialize and `collect=` was really the state write. Proof is arithmetic: `sync+local+ser+wr` failed to equal `rest` on **all 91 lines** of the user's log; after un-shifting, all 91 match exactly. Fixed at the source, and `tests/test_serialize_cost.py` pins the order of both the labels and the arguments.
- **Measured on the user's log (`[ov] build=8cf82896`)**: quiet match `avg_ms=0.288 frame_ms=4.22` (**237 fps**, tick 6.8% of the frame), and the tick fell from 1.62-2.12 ms to 0.29 ms after the gather caches. `[font] loaded=` reports all eleven name fonts present, including `himalaya.ttf` (Tibetan). `[sys:vis] near=0` across a full match: no cover hits are landing on targets, so the 0.75 m rule is not eating anyone.
- **The gather stops re-deriving a prop's verdict every frame.** In the user's log the gather was `0.775 ms` of a `1.64 ms` tick with `walk=105` and `items=5` - about a hundred props, each costing a position read plus six avatar-marker reads before being rejected, sixty times a second, to answer a question that is a property of the entity's class. The verdict is now cached per entity id (`COMBAT_CACHE_TTL = 0.5 s`), consulted **before** the position read, and dropped when the space changes. A cached prop costs one dict lookup; a cached target skips the classifier but is still projected and drawn.
  - Motion sampling moved behind the distance cull - it was being paid for every prop in the space - and the per-entity `_front` test is computed once instead of three times (head, feet, and the box).
  - The 0.5 s TTL is what bounds the one case that could go wrong: an entity that becomes a target while cached as a prop. New spawns are new ids and are classified on sight, so a parachuting player is not affected.
- **The aim path stopped re-reading the muzzle speed per target per tick.** `_calc_ballistic_velocity` sat inside `_estimate_lead_position`, so `_current_case` plus up to twelve attribute reads through the weapon prototype chain ran once per target per tick (`track=0.446` in the same log). It is cached on the weapon case identity with a 0.5 s TTL, a swap is picked up on the next tick, and a *miss* is never cached, so a prototype that gains a speed attribute cannot silently disable lead.
- **`[sys:tick]` now splits `rest`**: `sync=` (damping), `local=` (local avatar), `ser=` (packet), `wr=` (state write). `rest=0.334` was four different calls wearing one number, and the `[sys:perf]` line that was meant to break it down only fires above 60 ms - it has never once appeared in a log.
- **The missing-glyph logger found the real characters: Tibetan ༺ ༻.** The build with the IPA ranges covered `ʚ` - no complaint about U+029A in the log at all - and then named `U+0F3A` and `U+0F3B`, which are the ornate brackets players wrap their names in. The Tibetan block (`0x0F00..0x0FFF`) is now in `fontcov::Symbols()`, along with Lao and Myanmar, and the fallback list gains `himalaya.ttf` (Microsoft Himalaya is the only stock Windows font with Tibetan) and `arialuni.ttf` if Office installed it.
- **`[font]` now names the fonts that loaded**: `loaded=seguisb.ttf,msyh.ttc,tahoma.ttf,...`. Eleven files are tried and a missing one contributes nothing and says nothing, so "Thai renders" and "Thai cannot render" looked identical in a log. `families=` was useless for this - merged fonts share one `ImFont`, so it always read 4.
- **`[sys:vis] near=`** counts cover hits that landed within two metres of the aim point. If `near` tracks `cover`, the ray is stopping on the target's own geometry - a body with no owner id, or a hit position that is not the point the ray struck - and a target in plain sight is being reported as hidden. `cover` was 164 of 164 checks in one window of the user's log, which is either a corridor fight or a threshold that is too tight; this tells the two apart.
- **Frame rate on the symbol build, 105 entities and 5 targets on screen**: `tick=1.62-2.12 frame_ms=5.53-6.21` (161-181 fps), `gather=0.78-0.86 bone=0.25-0.30 track=0.43-0.82 rest=0.33`. The tick is 30% of the frame with five targets, and the frame is dominated by the game.
- **Names are drawn like the game's own nameplate**: bold text, black outline on all eight sides, no plate behind it, in the target's name colour. Only the name changed - the knocked/team/weapon/distance chips keep their plates, and the halo is nine text draws for one line per target, not per chip.
- **Every overlay log now starts with the build it came from**: `[ov] build=27d2d4c packet_v=11`. `CMakeLists.txt` derives it from `git rev-parse --short=8 HEAD` (and appends `-dirty` for a local build), so "are you running the fix" stops being a round trip. Last round it was answerable only by inference: the log showed `cover=0` with 31 vis lines, which only the older build can produce.
- **`[sys:vis]` splits the two ways a check can produce no answer**: `nocam=` is "the camera was not available", `no-ray=` is "no aim point to ask about", `err=` is the first exception. The counters are now reset together with the log (`range(5)`), so the parts always add up to `checks=`.
- **Frame rate, measured on the fix**: a quiet match is `frame_ms=4.31-4.48` with `tick=0.46-0.55` (232 fps), a one-target fight `frame_ms=4.53 tick=0.95`, and the lobby `rest=0.27-0.34` with `tick≈0.45`. The tick is now ~10% of the frame instead of ~70% of it.
- **Names keep their symbols: "KNS ʚ Saejin" now draws the tag.** The glyph ranges jumped from Latin-1 straight to Greek (`0x0100..0x024F`, then `0x0370`), so the whole band in between - IPA extensions (`ʚ ʕ ʔ`), spacing modifier letters (`˅ ˖ ˚`), combining marks, and the phonetic-extension block that small capitals (`ᴠ ᴋ ᴀ`) come from - was baked as nothing. A codepoint with no glyph is skipped by `AddText` without a word, so the tag simply disappeared and the name read as "KNS  Saejin". `fontcov::Symbols()` covers those blocks (plus Greek extended, superscripts, number forms, maths symbols A/B, Latin extended C/D, combining half marks) and the name font asks for them.
  - Any character still missing is now **named in the log** instead of vanishing: `[font] no glyph for U+029A in "KNS ʚ Saejin" - add that block to fontcov::Symbols()`, once per codepoint. The lookup asks the baked font for the glyph and compares codepoints, so a font that is simply not drawn yet is not reported as missing.
  - `[font] atlas=WxH families=N esp-glyphs=N` on the first frame reports what the atlas actually came out as, and a name font that failed to load shows up as `families=1`.
- **The frame rate is back**: `[sys:tick]` in the user's log went from `rest=6.2-7.9` to `rest=0.16-0.36`, so a 8-target fight is `tick=2.27 frame_ms=8.81` and a quieter one `tick=1.58 frame_ms=6.96`, against `tick=8.2-9.7 frame_ms=13-15` in the build that regressed.
- **`[sys:vis]` was mislabelling cover as `none`**: the cover outcome was never assigned, so every blocked ray fell through to the default. `cover=` in the log is now the real cover count; `none=` means what it says - no camera, or a ray that could not be cast. The behaviour was always right, only the tally was wrong.
- **The frame rate regression is mine: a failing `import` inside a per-tick function.** `[sys:tick]` named it in one line - `in_match=0 rest=6.187` and `in_match=1 rest=6.693` next to `gather=1.691 track=0.348` - i.e. a constant 6-8 ms in the window between the aim path and the end of the tick, which is exactly where the state snapshot is written.
  - The previous build replaced the snapshot write with a mapping, and imported `mmap` **inside** the write. The game's Python has no such module (its importer rejects anything not already loaded - the same hazard `_init_ctypes_shm` documents), so every tick paid a full failed importer search across `sys.path` plus open/fstat/truncate/close: 0.3 ms became 6.2-7.9 ms and halved the frame rate in the range and in a match.
  - The write path now imports nothing, keeps one **unbuffered** handle open for the life of the process and writes only the bytes it packed - one syscall, no 64 KB pad, no flush. A failed open is remembered instead of retried. `tests/test_state_write.py` now covers the open-once/unbuffered/no-import rules and the failed-open latch, and `test_nothing_is_imported_or_padded_in_the_write_path` fails if anything sneaks back in.
- **`[sys:vis]` says most visibility raycasts are not completing**: `checks=443 cleared=3 hit-target=84 cover=0 none=356`. The checks that do run now get the right answer (the airborne case), but 80% of them end in the exception path, which the ESP can only read as "not visible". The line now carries the first exception (`err=<type>: <message>`), so the next log says what it is instead of this being another theory.
- **Airborne and jumping targets are visible now: the raycast was asking for triggers.** `_line_of_sight_query` mirrors the game's own `IsVisible` (`gclient/framework/util/assist_aim_util`): cast from the camera to the aim point with `PHYSICS_SHOOT_TEST` and accept it when the hit body's owner id is the target. That is why walls and floors were always right.
  - `Space.RawRaycast(..., with_trigger=True)` resolves to `ClosestRaycast`, which returns the nearest hit **of any kind** - trigger volumes included. A player under a parachute or mid-jump is inside a skydive/air-drop trigger, so the nearest hit was the volume (owner id 0), not the player, and someone in plain sight was reported as "behind a wall" until the moment they landed and left the volume. That is the reported behaviour exactly, including that the aim's visibility check refused to fire at them.
  - It now calls the no-trigger variant (`ClosestRaycastWithoutTrigger`), which is what the game uses wherever it wants geometry. A ray that reaches the target point without hitting anything blocking now means `visible`; a hit whose position is within 0.75 m of the target counts as the target even when its owner id does not match (parachute canopy, hitbox shell); anything nearer is cover, as before.
  - `[sys:vis] checks= cleared= hit-target= cover= none=` every 10 s says which of those cases is actually happening, so the next log is evidence rather than agreement. Tests: `tests/test_point_visibility.py` - no-trigger flag, clear ray, cover, hit-at-target, and a failed raycast not claiming sight.
- **Where the frame rate got to** (the user's log from `e0bf2be`, the build before this one): a 7-target fight is now `frame_ms=7.17` (139 fps) with `tick=2.70 gather=1.50 track=0.72 rest=0.39`, against `frame_ms=9.77` (102 fps) and `tick=3.71` in the build before that. A match with no targets on screen: `frame_ms=4.77` (209 fps), `tick=0.99`. The range: 246-251 fps. The per-entity gather cost fell from 20.9 us to 16 us; the walk over the general pool (44-68 entities at ~1.7 us per engine read) and the aim path's 0.7 ms are what is left.
- **Found the gather's real cost: 18-21 us per entity, and it was 22 engine reads to answer "no".** The user's big-map log splits it for the first time: `gather=2.571 collect=0.130 proj=0.097 team=0.067 bone=0.378 items=7 walk=91` - the four measured pieces add up to 0.67 of 2.57 ms, and the remaining 1.9 ms is 20.9 us per entity. The same walk in the lobby costs 2.4 us per entity with the same code and the same entity count, so it is not the walk, the projections or the bones: it is the classification, and it is only expensive on real match entities.
  - `_is_combat` opened with `_is_skill_object` - thirteen marker reads - and `_is_vehicle` - three more - before it ever asked whether the entity was an avatar. Every billboard, water snare and magic field in the map paid all sixteen to be told no. The exclusions now sit **behind** the avatar test: `not (skill or vehicle) and avatar` is the same boolean in either order, so this is free. A prop answers in six reads; `_ai_kind`'s four more now also wait until something has been classified as a target at all.
  - Tried and reverted in the same build: a class-name gate at the top of the loop that would have skipped the general pool's props before any read (a string compare instead of ~10 engine reads). It is a big win on paper, but the ESP filter tests caught it dropping entities whose class name the list does not know - exactly the silent-disappearing-target failure mode this must never have. Not worth ten frames.
- **The state snapshot is a memcpy now.** `rest=` was 0.23-0.35 ms of every tick because each snapshot was padded out to the full 64 KB file and flushed through a buffered handle on the game thread. The padding was never needed - the overlay reads the entity count from the header and stops - so the runtime maps the same file the overlay maps and copies only the ~7 KB it actually packed. Test: `tests/test_state_write.py`, which runs the real function against a temporary file.
- **The projection is confirmed in draw units, and the flicker in the skeleton gate is gone.** The user's log from the fixed build: `[proj] samples=8 best=fwdxup,vfov mean_err_px=0.04 max_err_px=0.06 fov=106.2 draw=1920x1080 state=1334x750` - hundreds of rows at 0.00-0.07 px, always the same variant, and the two sizes side by side are the units bug in one line (`1334/1920 = 0.695`, matching the 0.58-0.64 measured off the screenshot). The gate that disables the skeletons, though, was flipping **six times in one session** - six ten-second holes - because a single-target row can read 57 px on its own. It now ignores rows with fewer than three targets and needs two bad rows in a row to stop drawing, so a real break is still caught and a bad frame no longer blinks.
- **`[sys:tick]` now splits the gather**, because after the last two builds it is the only thing left: `gather=2.975 track=0.614 rest=0.604 bone=0.486 items=15` in a 9.77 ms frame, against `gather=0.19 track=0.001 items=0` when the range is empty. The new fields - `proj=` (both engine projections per target), `team=` (team id plus faction relation), `collect=` (the walk over the whole space) and `walk=` (how many entities that walk found) - say which of them the ~0.19 ms per target actually is, instead of a fifth guess. No behaviour changed to get them.
- **Silent aim is back: the trajectory is on every tick again.** The previous build rate-limited `_update_cam_trajectory` to 60 Hz on the reasoning that the items it solves against are at most 16 ms old. That was wrong, and the code says why: `_update_cam_trajectory` is not the ESP. It publishes `_ray_target`, holds `_track_busy` true for the silent-aim redirect in `_query_corrected_ray`, and integrates the view turn with `dt`. At 145 fps the limit skipped roughly every other tick, and a skipped tick runs the `else` branch that sets `_track_busy = False` - so the redirect returned the *unmodified* ray on about half of all frames. The gate is gone, the tick is byte-identical to the build that worked, and `tests/test_silent_aim_tick.py` now drives three 6.9 ms ticks and fails if the trajectory is called fewer than three times or if `_track_busy` ever drops between them.
  - The gather stays rate-limited at 60 Hz, which is safe for a different reason: stale item positions are predicted forward by `_estimate_lead_position`. Nothing else on the aim path is throttled, and nothing else will be.
- **The skeletons floated away from their players because the projection was in the wrong units.** The game reports `gui.cocos_screen_size` - a design/render resolution - which is not the size of the frame the overlay draws into. The user's screenshot measures it exactly: every skeleton vertex sat at **0.58-0.64 of its true pixel position, on both axes, about the top left** (five players, `kx=0.583..0.640`, `ky=0.614..0.640`) - a uniform 0.62x scale, the right shape in the wrong size. Measuring from `ImGui::GetIO().DisplaySize` instead, as the reference overlay does, puts them back on the bodies.
  - The previous cross-check could not see it, and that is the interesting part: it multiplied the engine's answer by `g_state.screen_w/h` and the projection divided by the same numbers, so a scale error cancelled on both sides and it cheerfully reported 0.03 px while the skeletons were 40% off. It now compares in the draw list's own units, and logs both sizes (`draw=1463x782 state=907x485`) so the next log can never hide a mismatch like this again.
  - The calibration now also **picks** the variant the draw uses (`g_proj_best`) instead of just recommending one, so handedness and the fov axis are a runtime measurement rather than a constant that has to be kept in sync with a log line.
- **Thai names render.** Thai is in neither Segoe UI nor Microsoft YaHei, so a name written in Thai drew as empty boxes: `GetGlyphRangesThai()` is now in the name atlas and Leelawadee UI / Leelawadee / Tahoma are merged into the name font as fallbacks.
- **The skeleton is projected by the overlay now, and the measurement that licensed it.** Cross-checked against the native overlay in the user's friend's project: it reads a camera position, a 3x3 basis and a fov from memory and projects with `focal = 1/tan(fov/2)`, `x = cx + (px/pz)*focal*screenH/2`, `y = cy - (py/pz)*focal*screenH/2`. We already receive the camera position, forward vector, fov and screen size in the state packet, so the overlay can do the same maths. Two details are not written down anywhere - the handedness of the basis (we derive it from world-up, since the world is Y-up) and whether the engine's fov is vertical or horizontal - so the previous build measured all four combinations against the engine's own answer: `[proj] samples=5 mean_err_px=0.03 max_err_px=0.04 fov=106.2 screen=1334x750`, with the winner at 0.01-0.19 px per sample and the other three conventions 59-652 px out. The winner is `right = forward x up` with the focal from the **vertical** fov, which is exactly what the reference overlay does.
  - Skeleton joints now travel as **world-space xyz** (`ENT_FMT` `32f` -> `48f`, `VERSION` 10 -> 11, `sizeof(Ent)` 312 -> 376 pinned by `static_assert`), and the overlay projects them itself - one camera frame per frame, not one engine call per joint. That removes sixteen `WorldToScreenPercent` calls per skeleton per gather from the Python side; the phase timer's new `bone=` column is what that used to cost (up to 0.43 ms per tick).
  - The head and feet stay on the engine's projection, so boxes, names, arrows and the visibility colour are unchanged; the calibration keeps running every 10 s against those, and now it also **gates** the new path: if the error ever climbs past 40 px the skeletons switch themselves off (`[proj] ERROR too large - skeletons disabled`) instead of drawing in the wrong place.
  - The variant labels and their arguments were in two places and disagreed - the first log named the wrong winner. They are one table now, and a test fails if they are ever derived separately again.
- `[sys:tick]` now also reports `bone=`, the share of the gather spent fetching and projecting skeleton joints. The other internal's numbers come from the same place: one camera sample per frame instead of one per bone, a cap on how many players are projected at all, and cheap rejections before expensive reads.
- **The tick is now 0.4-0.9 ms where it was 8.5.** The user's log shows both ends of it: `21:59:42 avg_ms=0.407 frame_ms=4.91 in_match=1 gather=0.026` - a 204 fps frame with 0.4 ms of runtime in it - and `22:00:02 avg_ms=4.506 frame_ms=10.05 gather=2.769 track=0.892 rest=0.693` in a fight. In other words the fix works, and what is left scales with how many entities are on screen, which is the gather. This build attacks that:
  - the gather runs at **60 Hz** instead of once per frame (the ESP is a 60 Hz overlay in effect; at 100 fps that halves its cost per frame and it keeps falling as fps rises);
  - a **skeleton costs sixteen joint lookups plus sixteen projections**, so only the nearest **ten** on-screen targets get bones - everyone visible still gets their box, name and team label;
  - `_update_cam_trajectory` and the damping syncs run at the gather cadence instead of every frame;
  - the unlock/cosmetics pass runs at **2 Hz**, not per frame: it measured 0.45-0.5 ms per frame in the lobby and produced the `max_ms=70.338` outlier when it rebuilt;
  - `[sys:tick]` now also reports `items=N`, so the next log ties cost to scene size directly.
- Honest limit: the runtime is Python running on the game's own thread. Its remaining per-frame work is dominated by engine calls (position, joint, projection per entity), so there is a floor of roughly a millisecond in a busy fight; the light-scene 0.4 ms figure is what the code costs when it is not gathering. Getting below that in a fight means moving the gather out of Python, not another micro-optimisation.
- **Match frame rate: 68 -> ~105 fps with the offscreen-bone fix, and this build cuts the rest of the tick.** The user's `[sys:tick]` went from `avg_ms=8.535 frame_ms=13.39` to `avg_ms=4.265 frame_ms=9.57`, and the phase split said where the remainder was: `apply=0.881 gather=2.597 track=0.545 rest=0.236`. Four changes:
  - the distance filter now runs **before** classification, so entities outside the ESP range no longer pay for ~two dozen flag checks each;
  - the head joint is only fetched for targets **in front of the camera** (an arrow needs a direction, not a joint), which removes the last per-entity joint call;
  - the "is this class a CombatAvatar" MRO walk is cached per **type object**, which cannot change; the per-instance flags stay fresh so a live entity that turns into a skill object is still dropped immediately;
  - skin/theme reconciliation runs at 5 Hz instead of every frame (it was 0.88 ms of `apply=` for a change the player cannot see), and the gather is capped at 120 Hz (`interval = 1/120`) instead of once per frame.
- The `FATAL` lines in `runtime_fatal-5.txt` (engine importer failing on `moba_faction_calculation`, `icombat_data.on_setattr`) are not new: the same traces are in `runtime_fatal-2.txt` and `-4.txt` from earlier sessions, and they are the game's own importer, not the runtime.
- **Found it: the runtime was taking 8.5 ms of a 13.4 ms frame.** `[sys:tick] n=747 avg_ms=8.535 max_ms=13.469 frame_ms=13.39 in_match=1` - the Python tick that runs on the game thread was spending 64% of the frame budget, which is exactly why a match sat at 68 fps while the same machine reads 235 fps with another internal, and why the range (few entities) looked fine. The overlay's own cost never was the problem: `overlay_avg_ms=0.49`.
- The cause was the gather: sixteen skeleton joints were sampled for **every** entity inside the scan distance - around 1700 engine calls per frame in a full match - including entities that were nowhere near the screen. Two changes, no behaviour lost: skeleton joints and the weapon name are now sampled only for targets that are actually on screen (offscreen targets are still gathered, because the offscreen arrows need their position), and the ESP path lets a joint's world transform be up to one frame old (`ttl=0.016`) while the head and the whole aim path keep the original 8 ms, where a stale hitbox would matter. The skeleton is projected with the current camera every frame, so it stays glued to the box.
- `[sys:tick]` now carries the phase split - `apply= unlock= gather= track= rest=` in milliseconds - so the next log says which phase is left instead of another round of guessing. Test: `tests/test_gather_cost.py`.
- **In-match, the frame rate is the game's own: `19:19:24 fps=67.2 sync0=844 sync1=0 ... overlay_avg_ms=0.493`, against a screenshot of the same match showing `FPS: 68`.** The game already presents with `sync=0` there, so the vsync override correctly does nothing - which is why the switch made no difference in a match. It *did* do its job in the lobby, where the game does present `sync=1`: `19:57:18 sync0=1689 sync1=0 fps=176.7`, up from 60. The "200+ in the range" is a scene difference, not a build difference: the same session logs `ents=0` in the range and 68-100 space entities in a match (`CombatAvatar=16, CombatAvatarMoba=14, ...`).
- **The runtime's own per-frame cost is now measured, because it was the last unknown.** `[sys:perf]` only fires for a tick over 60 ms, so the tick that actually runs on the game thread sixty times a second had never been timed - and that is the only place the runtime could be costing frames. `[sys:tick] n=600 avg_ms=0.083 max_ms=3.114 frame_ms=16.67 in_match=1` now says, every ten seconds, what the tick costs and how often the engine calls it: `avg_ms / frame_ms` is the share of the frame the runtime takes. Two float adds per tick, logged with `force=True` so the log throttle cannot hide it. Test: `tests/test_perf_scene.py`.
- **The 60 fps is the game's own present call, and the log now proves it instead of arguing about it.** In the user's own session: `sync1=600` out of 600 frames with `overlay_avg_ms=0.910 / ui_avg_ms=0.692`, and later `sync1=598` with `overlay_avg_ms=0.013 / ui_avg_ms=0.000` - the overlay doing thirteen *microseconds* of work per frame while the game sat at 60. In the same run, the moment the game presented with `sync=0`, the frame rate went to 226 (`sync0=1322 fps=226.1`). With entities on screen (8 players) the overlay is still 0.3-0.4 ms, about 0.03 ms per entity. The forum advice to cap the overlay's drawing at 120 Hz would have saved 0.4 ms of a 16.7 ms frame.
- **New, opt-in: "Ignore game V-Sync" (Settings -> Performance).** The sync interval is the only thing about the frame rate the overlay actually controls, so when the game asks for `sync=1` this forwards `sync=0` instead. Off by default - it tears and it defeats G-Sync/FreeSync - and narrow: only `sync == 1` is touched, nothing else about the game's Present is changed. The perf line now reports the interval that was *presented*, and one `vsync override: presenting sync=0 (the game asked for 1)` line makes it visible in the log. Test: `tests/test_vsync_override.py`.
- **The perf line now says what the frame rate was measured on.** `fps=60` is the same number whether the map is heavy, the game asked for vsync, or our own per-entity drawing is the cost, so the 10-second line now carries `ents=N menu=0/1 esp=0/1` next to `sync0`/`sync1` and the cost split (`overlay_avg_ms`, `ui_avg_ms`, `state_avg_ms`). One match and one range session then answer the question instead of a theory: overlay cost flat at a few tenths of a millisecond while `fps=60` means the frame rate is not ours, and cost that climbs with `ents` means it is.
- **The swap chain's mode and the desktop's mode are logged side by side.** `[display] swapchain=2560x1440 chain_hz=60 windowed=0 effect=0 flags=0x0 desktop=2560x1440 desktop_hz=144`. A game can put the panel into a different refresh rate for a match than the desktop runs at - and if the chain says 60 Hz, 60 fps is the ceiling no matter what the overlay does.
